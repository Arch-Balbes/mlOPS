# ML-манифест: прогноз ETA доставки

**Уровень зрелости ML-системы: 2**

Компоненты уровня 2: версионирование кода, CI/CD, feature store (PostgreSQL), API-сервинг, мониторинг качества, MLflow, Airflow.

---

## 1. Предыстория

Маркетплейс обещает клиенту окно доставки при оформлении заказа. Текущие правила (фиксированные минуты на зону) не учитывают загрузку курьеров, расстояние и время суток. В результате ~18% заказов приходят вне обещанного окна: рост звонков в поддержку, отмены и штрафы партнерам. Заказчик хочет автоматизировать прогноз времени доставки (ETA) и безопасно обновлять модель без простоя сервиса.

## 2. Ценностное предложение

Система дает реалистичный ETA на этапе checkout, снижает число опозданий и переносов, разгружает call-центр и повышает NPS. Операционная команда получает единый пайплайн переобучения с контролем качества и откатом при деградации метрик.

## 3. Цели

| # | Задача |
|---|--------|
| 1 | Предсказывать `delivery_minutes` с MAE, достаточным для окна +/-15 мин |
| 2 | Обслуживать checkout в реальном времени (p95 latency API <= 2.5 с) |
| 3 | Ежедневно переобучать модель на актуальных фактах доставки |
| 4 | Выкатывать новую модель через canary и выводить из эксплуатации при провале gate |
| 5 | Мониторить дрейф признаков и качество предсказаний онлайн |

## 4. Решение

**Входит в продукт:**

- Регрессия ETA (LightGBM / sklearn), baseline: медиана по складу
- ETL: заказы, маршруты/курьеры, события доставки
- Feature store: PostgreSQL (`features_eta`)
- Сервинг: FastAPI `/predict`, canary через `MODEL_URI` / веса
- MLflow: эксперименты и Model Registry (`Staging` -> `Production`)
- Airflow DAG: ingest -> features -> train -> register -> deploy
- Prometheus: latency, MAE rolling, счетчики предсказаний
- Grafana: дашборды SLI/SLO
- IaC: Docker Compose + Terraform (опционально)
- **Внешний доступ:** только Grafana через tunnel4 (`localhost:3000`); API/MLflow/Airflow — localhost

**Ограничения:** учебный стенд на синтетических данных; prod-поток эмулируется batch-джобой.

## 5. Осуществимость

Реализуемо за 3-4 недели силами 1 ML-инженера и 1 DevOps. Стек: Python 3.11, PostgreSQL, MLflow, Airflow, FastAPI, Docker. Runtime на домашнем ПК (Docker Compose); синтетический генератор заменяется подключением к DWH без смены контрактов таблиц.

## 6. Данные

| Назначение | Источник | Описание |
|------------|----------|----------|
| Обучение | `data/raw/*.parquet`, история 6-12 мес | orders, routes, delivery_events |
| Прод / онлайн | PostgreSQL `eta_db` + API `http://localhost:8000` | новые заказы + отложенные метки из `delivery_events` |
| Разметка | Автоматическая | label = `(delivered_at - order_created)` в минутах; классы не требуются (регрессия) |

Таблицы: `orders`, `routes`, `delivery_events`, `features_eta`.

## 7. Метрики (приоритет)

1. **On-time delivery rate**: доля заказов в обещанном окне +/-15 мин (бизнес)
2. **Среднее отклонение факта от ETA** (бизнес / продукт)
3. **p95 latency API** (техника / UX checkout)

## 8. Оценка качества модели

**Офлайн:** MAE, RMSE, `%_within_15min` на hold-out; сравнение с baseline; gate: MAE <= baseline * 1.05.

**Онлайн:** rolling MAE за 7 дней, PSI по `distance_km`, доля предсказаний с ошибкой > 30 мин, correlation pred vs actual.

## 9. Подбор модели

Итерации: (1) медиана по `warehouse_id` -> (2) LinearRegression -> (3) LightGBM с grid n_estimators / max_depth. Лучший run в MLflow; артефакт в Registry.

## 10. Инференс

- **Real-time:** POST `/predict` при создании заказа (чтение фичей из FS + модель)
- **Batch:** ночной DAG: переобучение, backfill фичей, deploy

## 11. Обратная связь

Через 24-48 ч после доставки в БД появляется `delivered_at`, затем пересчет label и следующий train.

**MDD для принятия решений: Да.** Rollout и оптимизации (кэш, ONNX) по p95 latency и on-time rate, не только по offline MAE.
