# Metrics Driven Development: оптимизация latency ETA API

## Контекст

При checkout маркетплейс вызывает `POST /predict`. Задание сравнивает распределения latency:

- **Существующая система:** N(μ=3.5 с, σ=0.4)
- **Улучшенная система:** N(μ=2.0 с, σ=0.4)

## Решение по MDD

### 1. Метрика-цель

**Primary:** p95 `eta_predict_latency_seconds` <= 2.5 с (SLO)  
**Guardrail:** rolling MAE <= baseline * 1.05, on-time rate не падает > 0.5 п.п.

### 2. Наблюдения (синтетическое сравнение)

| Перцентиль | Старая (с) | Новая (с) | Разница |
|------------|------------|-----------|---------|
| p50 | ~3.5 | ~2.0 | -1.5 |
| p95 | ~4.2 | ~2.7 | -1.5 |
| p99 | ~4.6 | ~3.1 | -1.5 |

Сдвиг распределения влево уменьшает долю запросов > 2.5 с с ~25% до ~5%.

### 3. Бизнес-гипотеза

10 000 checkout/день: +1 с latency дает +0.2% отказов от оформления, около 20 потерянных заказов/день.  
Снижение p95 с 4.2 до 2.7 с дает экономию порядка 15-20 заказов/день (допущение для учебного проекта).

### 4. Инициативы (приоритет impact * effort)

| # | Инициатива | Ожидаемый эффект на p95 |
|---|------------|-------------------------|
| 1 | Кэш фичей в PostgreSQL / in-memory по `warehouse_id` | -0.3-0.5 с |
| 2 | Warm workers uvicorn, preload модели | -0.2-0.4 с |
| 3 | LightGBM -> ONNX / меньше деревьев | -0.1-0.3 с |
| 4 | Canary только после A/B метрик | контроль риска |

### 5. Критерий rollout улучшения

**Катим**, если за 7 дней canary:

- p95 < 2.5 с
- on-time rate >= baseline - 0.5 п.п.
- MAE <= baseline * 1.05

**Не катим**, если MAE вырос при улучшении latency: guardrail MDD блокирует деплой.

### 6. Следующая итерация

После деплоя: мониторинг `eta_predict_latency_seconds` и `eta_abs_error_minutes` в Prometheus; еженедельный review в формате MDD (метрика -> гипотеза -> эксперимент -> решение).
